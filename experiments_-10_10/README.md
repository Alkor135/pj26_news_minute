## Согласованная разметка: величина × качество

Обозначения: `D = abs(points)`, `z = z_score`, `A` — сила движения,
`Q` — качество траектории. Используются метрики `source/price_reactions.py`.

```text
A = min(1, z / 2)
Q = min(1, er / 0.45, direction_fraction / 0.70,
        D / (2 * mae_points), D / (2 * max_pullback_points))
```

При нулевом `mae_points` или `max_pullback_points` соответствующий член
принимается равным 1. Качество определяется самым слабым из четырёх признаков.

Правила применяются в следующем порядке:

1. Неполное окно или отсутствие валидной предшествующей волатильности/`z_score`
   означает «нет метки». Пропуски не заменяются нулём.
2. `stable = True` даёт `10 * sign(points)` по существующему фильтру.
3. Для остальных полных окон `z <= 0.25` даёт 0. Это стартовый порог из
   согласованного предложения; его распределение нужно проверить на истории
   до сентября 2026. Для нейтральной реакции `Q` не требуется: при `points = 0`
   некоторые показатели траектории в существующем коде закономерно отсутствуют.
4. Вне нейтральной зоны требуются все показатели качества. При их отсутствии
   метка не назначается. Иначе модуль балла равен
   `min(9, max(1, floor(10 * A * Q + 0.5)))`, знак определяется `points`.
   Округление половины вверх фиксирует однозначное техническое правило.

Сильное движение с глубокими откатами может получить лишь ±2–4. Значения
±8–9 требуют большой величины и высокого качества. Без `stable` получить
±10 нельзя, в том числе при округлении. Существующий `stable` не пересчитывается
по новой формуле: сохраняются его исходные условия и параметры нейтральной зоны
в пунктах. Новая нейтральная зона по `z` относится к экспериментальному баллу.

Вместе с баллом сохраняются исходные метрики, `stable`, параметры расчёта,
версия разметки и причина отсутствия метки. Балл не является вероятностью или
доходностью. Нулевой итог не исключает больших колебаний внутри окна.

Оценка задаётся отдельно для каждого инструмента и горизонта. Будущие котировки
используются только для целевой разметки. Признаки и фильтры при прогнозировании
должны быть доступны на момент получения новости.

## Скрипты обучения

| Скрипт | Начальная модель | Пакет на GPU | Накопление градиентов |
| --- | --- | ---: | ---: |
| `train_RTX4070.py` | `Qwen/Qwen3-4B-Instruct-2507` | 1 | 16 |
| `train_RTX3090Ti.py` | `Qwen/Qwen2.5-7B-Instruct` | 2 | 8 |

`source/training_common.py` содержит общую проверку данных и обучение. Оба профиля
используют QLoRA NF4, ранг 16, длину 512 токенов, начальную скорость `1e-4`
и одну эпоху. Это стартовые настройки, а не подтверждённые оптимальные значения.
Базовые веса заморожены; обучаются LoRA-матрицы в слоях внимания и MLP.
Один адаптер обслуживает оба инструмента и все пять горизонтов.
Профиль не запрещает запуск на другой NVIDIA-карте; фактическая GPU записывается
в отчёт. При нехватке памяти уменьшают `--batch-size` или `--max-length`;
проверка не должна незаметно обрезать целевой ответ.

Вход модели: заголовок новости, инструмент, горизонт. Целевой ответ
по умолчанию — `{"class":"positive"}` (допустимы `negative`, `none`, `positive`).
Для `--task score` сохраняется ответ вида `{"score":4}`.
Модель учится на токенах ответа; вход маскируется в функции
потерь. Будущие метрики, `stable`, даты завершения окон и фактический балл
не входят в запрос. Это supervised fine-tuning генерации ответа с causal
cross-entropy; такая функция потерь не задаёт числовое расстояние между баллами.
Поэтому для `score` считаются MAE и ошибки формата, а для `extremes` —
precision/recall/F1 каждого класса, число ложных сигналов и пропусков.
Повторение редких обучающих примеров не добавляет независимых событий
и не гарантирует улучшения. Балансировка проверяется на естественной валидации.

### Формат входа

Одна строка CSV или один JSON-объект на строку JSONL — одно сочетание
новости, инструмента и горизонта. Кодировка UTF-8. Минимальный пример:

```json
{"news_id":"example-1","title":"Заголовок новости","loaded_at":"2026-07-15 12:00:00","end_at":"2026-07-15 12:05:01","instrument":"MIX","horizon":5,"score":4,"stable":false,"score_version":"magnitude-quality-v1","group_id":"event-1"}
```

Пример иллюстрирует формат и не является реальной размеченной новостью.

- Обязательны `news_id`, `title`, `loaded_at`, `end_at`, `instrument`, `horizon`,
  `score`, `stable`, `score_version` для размеченных строк.
- `loaded_at` — первое получение новости, `end_at` — плановый конец полного
  окна реакции из расчёта, а не время последней сделки `exit_at`.
- Время без смещения считается временем МСК; ISO-время со смещением переводится
  в МСК. `instrument`: MIX/RTS; `horizon`: 5/15/30/60/120; `score`: целое −10…10.
- `stable` — JSON true/false; в CSV допустимы true/false или 1/0.
  `abs(score) == 10` должно точно соответствовать `stable`.
- Отсутствующий `score`/null/пустая ячейка означает отсутствие метки: строка
  пропускается с отдельным счётчиком. Ноль — настоящий нейтральный ответ.
- Если присутствует `status`, для размеченных строк он должен быть `ok`.
- `score_version` фиксирует формулу и параметры разметки; смешивать версии
  в одном запуске запрещено. При изменении порогов версия должна измениться.
- Необязательный `group_id` связывает перепечатки и переформулировки одного
  события. Без него обнаруживаются только точные нормализованные заголовки.
- Одинаковый `news_id` должен иметь одинаковые заголовок и время получения;
  повтор сочетания `news_id/instrument/horizon` вызывает ошибку.
- Исходные метрики рекомендуется сохранять в дополнительных столбцах:
  обучающий код их не добавляет в запрос к модели.

### Временное разделение

Начальные границы: обучение с 01.09.2025 до 01.08.2026, валидация с 01.08.2026
до 01.09.2026. Сентябрь 2026 не используется ни для обучения, ни для выбора

Счётчики удалений сохраняются; после фильтрации обе части должны быть непустыми.

Отложенная выборка остаётся обязательной, но её роль явно меняется с validation
на test. По умолчанию по-прежнему используется августовская валидация.

### Результаты и ограничения

По умолчанию результат сохраняется в `data/experiments_-10_10/RTX4070_extremes`
либо `data/experiments_-10_10/RTX3090Ti_extremes`. Для `--task score` сохраняются
прежние каталоги `RTX4070`/`RTX3090Ti`:

- `data_report.json`: распределения до и после балансировки, удаления, параметры
  и SHA-256 исходной разметки. На текущих данных — 96 negative, 93 positive,
  3804 none до балансировки, по 3804 каждого класса после; валидация — 613 строк
  без изменения (12 negative, 18 positive, 583 none).
- `training_manifest.json`: точная ревизия базы, GPU, параметры, версии библиотек.
- `adapter/`: LoRA-веса и токенизатор; это ещё не самостоятельная модель Ollama.
- `adapter_provenance.json`: после всех метрик фиксирует завершение обучения,
  SHA-256 адаптера и ревизию базы для проверки при экспорте.
- `training_metrics.json`: метрики обучения и loss на валидации.
- `classification_metrics.json`: для extremes — метрики классов и матрица ошибок;
  неверные ответы учитываются как пропуски. По умолчанию оценивается вся валидация.
- `score_metrics.json`, `validation_predictions.json`: метрики выбранной задачи
  и ответы модели с исходным фактическим баллом. Для score это MAE, доля некорректных
  ответов и исходные предсказания на фиксированной случайной подвыборке до 256
  валидационных строк (`--prediction-limit 0` проверяет все строки).

MAE рассчитывается по корректным JSON-ответам и обязательно рассматривается
вместе с долей ошибок формата. Нулевой прогноз сравнивается на тех же строках;
отдельно приведён его MAE по всей проверяемой подвыборке.
Файловых логов нет; прогресс идёт в консоль. Промежуточные checkpoint не сохраняются.
Каталог существующего обучения не перезаписывается; повторный запуск требует
другого `--output`. Отчёт `--dry-run` можно обновлять до начала обучения.

### Экспорт и импорт в Ollama

`export_ollama.py` принимает каталог **завершённого** обучения (`--run`).
При запуске без параметров, в том числе кнопкой VS Code, выбирается единственный
профиль `RTX4070`, `RTX3090Ti`, `RTX4070_extremes` или `RTX3090Ti_extremes`
с `adapter_provenance.json` в
`data/experiments_-10_10` относительно корня проекта. Если готовы оба профиля
или ни одного, скрипт выводит объяснение и предлагает явно указать `--run`.
Если сохранена старая и новая модель, каталог нужно указать явно.
Остальные проверки завершённости и SHA-256 сохраняются. Поле `task` передаётся
в экспорт, чтобы импорт и проверка использовали правильный формат ответа.
Путь llama.cpp по умолчанию — `data/experiments_-10_10/llama.cpp`;
его можно изменить через `--llama-cpp-dir`. Пример запуска без параметров:

```powershell
.\.venv\Scripts\python.exe experiments_-10_10/export_ollama.py
```

Он проверяет наличие адаптера, всех метрик и `adapter_provenance.json`, сверяет
SHA-256 весов и сопоставляет базу с
`training_manifest.json` и загружает точно записанную SHA-ревизию модели из
Hugging Face. Затем объединяет LoRA с неквантованной базой в FP16, сохраняет
полные Safetensors в `RUN/export/merged/`, преобразует их в F16 GGUF средствами
llama.cpp и квантует готовый файл (по умолчанию Q4_K_M). Сохраняются и F16,
и квантованный GGUF, чтобы можно было позже выбрать другое квантование. Итоговый
`export_manifest.json` содержит версии базы, SHA-256 адаптера и обоих GGUF и
параметры конвертации. Перед GGUF-конвертацией скрипт пробует один ответ
объединённой модели; результат записывается в `merged_smoke_test`. Если ответ
нарушает формат, экспорт остаётся доступен, а предупреждение требует отдельной
проверки качества. Публикация папки `export` происходит после успешного
завершения всех шагов; существующий каталог не перезаписывается.

Для экспорта нужны общее `.venv`, зависимости конвертера llama.cpp
и готовый `llama-quantize`. Полная последовательность первичной подготовки
для Windows описана в Obsidian:
[prepare_ollama_cpp.md](</C:/Users/Alkor/gd/Obsidian_Alkor/02_Projects_Проекты/Алготрейдинг/pj26_news_minute/prepare_ollama_cpp.md>).
На этом компьютере подготовлены исходники и официальный CPU-квантизатор
выпуска `b11669` (SHA `620d2225cc436ab0b001e3200e590e3b286ef9ab`).
Применён готовый архив для Windows x64 с проверкой SHA-256, поэтому CMake
и компилятор не требуются. Зависимости GGUF, SentencePiece и Protobuf добавлены
в корневой `requirements.txt`. Настоящая конвертация синтетической Qwen3 в

Если зависимости конвертера конфликтуют с окружением обучения, установите их

Параметры экспорта: `--run`, `--output`, `--llama-cpp-dir` либо `--converter`

`Q8_0`), `--device` (`cpu`, `cuda:0`), `--check-only`. Проверка без весов
отвергнет каталоги, где пока есть лишь `data_report.json`; уже существующий
`export` не мешает повторной проверке исходного обучения.

`import_ollama.py` принимает каталог `RUN/export`
и автоматически выбирает его при запуске без параметров, если только один
из стандартных профилей `RTX4070`/`RTX3090Ti` содержит
`export/export_manifest.json` в `data/experiments_-10_10` относительно корня
проекта. Если таких папок нет или найдены обе, требуется явный `--export`.
Автоматический выбор сохраняет все проверки целостности и защиту от замены
существующей модели. Пример запуска кнопкой VS Code или из корня проекта:

```powershell
.\.venv\Scripts\python.exe experiments_-10_10/import_ollama.py
```

Скрипт проверяет сигнатуру GGUF
и его SHA-256, записывает в каталоге экспорта `Modelfile` с заданием из обучения, нулевой
температурой и ссылкой на локальный GGUF. Затем вызывает `ollama create` и
посылает пробный запрос через `/api/chat`. Ответ должен быть JSON ровно с
полем `class` со значением `negative`, `none` или `positive` для extremes
либо одним целым `score` в диапазоне −10…+10 для прежней задачи.
Результат проверки сохраняется в
постоянном `import_report.json`. Если имя уже занято, скрипт останавливается;
`--replace` разрешает явное обновление, не удаляя модель заранее. Если пробный
ответ неверен, скрипт сообщает ошибку и оставляет созданную модель для
диагностики. При `--check-only` Ollama не требуется и файлы не изменяются.

```powershell
.\.venv\Scripts\python.exe experiments_-10_10/import_ollama.py --export data/experiments_-10_10/RTX4070/export --check-only
.\.venv\Scripts\python.exe experiments_-10_10/import_ollama.py --export data/experiments_-10_10/RTX4070/export
.\.venv\Scripts\python.exe experiments_-10_10/import_ollama.py --export data/experiments_-10_10/RTX3090Ti/export --name news-score-3090ti
ollama run news-score-4070
```

Параметры импорта: `--export`, `--name` (по умолчанию `news-extremes-4070` либо
`news-extremes-3090ti` для классов; `news-score-*` для балльной задачи),
`--host` (по умолчанию `http://127.0.0.1:11434`),
`--ollama`, `--replace`, `--check-only`. Для обычного запуска должна работать
локальная служба Ollama. Один вызов модели оценивает только одну пару
«инструмент, горизонт»; десять сочетаний требуют десяти запросов.

Адаптеры двух разных моделей нельзя переставлять между их базами. Техническая
проверка формата не подтверждает прогнозную полезность: после квантования
нужно отдельно оценить модель на отложенных новостях.
Для проверки импортированной модели используется
`tests/experiments_-10_10/check_model.py` (по правилу проекта проверочные скрипты
находятся в `tests`). Запускается без параметров кнопкой VS Code или командой:

```powershell
.\.venv\Scripts\python.exe tests/experiments_-10_10/check_model.py
```

По умолчанию проверяются 32 сохранённых примера августовской валидации;
`--limit 0` проверяет всю сохранённую подвыборку. В режиме score скрипт сравнивает
MAE модели Ollama, нулевого прогноза и исходного адаптера; в режиме extremes —
метрики классов. В обоих режимах считает ошибки формата и
сохраняет `check_model_report.json` в каталоге обучения. Выбор модели и
подробности параметров описаны в `tests/experiments_-10_10/README.md`.
Первый режим extremes обучен пользователем и проверен на августе; отдельное
финальное обучение полного года пока не запускалось. Подробности проверок:
`tests/experiments_-10_10/README.md`.

### Оркестратор для RTX 4070

`orchestrator_RTX4070.py` последовательно запускает этапы 3–8 текущего эксперимента:
`build_rasmetka.py` → `train_RTX4070.py --task extremes` → `export_ollama.py`
→ `import_ollama.py` → `tests/experiments_-10_10/check_model.py --limit 0`
→ `build_html_report.py`.
Этапы 1–2 (чтение RSS и тематический фильтр) выполняются внутри разметки.
Подготовка `.venv` и llama.cpp по пункту 4.1 должна быть выполнена заранее.
Нужна работающая локальная Ollama для импорта и проверки.

```powershell
# Показать команды без выполнения
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --dry-run
# Полный запуск; разметка пересоздаётся
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py
# Удалить прежнюю разметку и сводку, затем выполнить полный цикл
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --delete-labels
# Для уже готовой разметки: обучение и все последующие этапы
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --from-stage 4
# Только обучение
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --from-stage 4 --to-stage 4
# Продолжить после завершённого обучения
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --from-stage 5
# Только HTML из уже готовых результатов, без Ollama
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --from-stage 8
```

`--from-stage` и `--to-stage` задают включительный диапазон 3–8.
`--data` выбирает JSONL, `--run` — единый каталог всех результатов
(по умолчанию `data/experiments_-10_10/RTX4070_extremes`), `--reaction-db`
передаёт готовую базу реакций разметке, `--name` задаёт имя для импорта и проверки
(по умолчанию `news-extremes-4070`). `--replace` разрешает замену этого имени
в Ollama, но не перезапись обучения или экспорта.
`--delete-labels` перед этапом 3 удаляет выбранный через `--data` JSONL и сводку
с именем `STEM_summary.json` в той же папке. Для стандартного пути это
`scores.jsonl` и `scores_summary.json`. Отсутствующие файлы пропускаются.
Флаг нельзя сочетать с началом на этапе 4–8. При `--dry-run` только показываются
пути удаления, файлы сохраняются. Удаление не затрагивает базы RSS, котировки,
адаптеры и экспорт. Если перед запуском обнаружено существующее обучение
или экспорт, препятствующее выполнению цепочки, разметка также не удаляется.
Запускается текущим Python из корня проекта, независимо от рабочего каталога.
Файловых логов нет; отчёты создают сами этапы в своих штатных каталогах.
При первой ошибке процесс останавливается с её кодом. Автоматического
возобновления обучения и пропуска уже выполненных этапов нет: выбрать
`--from-stage 5`, `6`, `7` или `8` для продолжения либо новый `--run` для повторного
обучения. Проверка существующего каталога обучения/экспорта выполняется до
запуска разметки, чтобы не пересчитывать её при невозможности продолжения.
Завершение этапов означает исправность запуска и формата, а не прибыльность модели.

заголовку/идентификатору и фильтровать по типу ошибки, инструменту и горизонту.
Метрики вычисляются по сохранённым ответам, а не берутся из общей accuracy.
Текст новостей экранируется. Заголовки добавляются только при совпадении SHA-256
разметки с исходным отчётом. Если разметки нет или её контрольная сумма другая,
HTML всё равно создаётся с идентификаторами и пояснением об отсутствии заголовков.

В начале HTML есть прямой ответ «Можно использовать для торговли?».
Текущий отчёт проверяет классы и условные результаты отдельных сигналов;
готовность к реальной торговле он не подтверждает, поскольку не моделирует
издержки, исполнение заявок, задержку ответа и совместный учёт позиций.
Это не означает автоматически, что каждый ложный экстремальный сигнал убыточен.

В отдельной таблице ложных `negative`/`positive` показаны заголовок, инструмент,
горизонт, фактический класс/балл, цены и время входа/выхода из разметки,
движение цены и совпадение направления. «Движение цены, пт» равно
`exit_price - entry_price`, «По сигналу, пт» равно этому движению для positive
и движению с обратным знаком для negative. Например, при отрицательном сигнале
падение −175 пунктов даёт условные +175 пунктов по сигналу.
Направление считается по ценам даже при фактическом балле 0.
Отсутствующие котировки отображаются как недоступные, не как нулевой результат.
Если обе цены и поле points присутствуют, их согласованность проверяется.

Пункты — единицы исходной котировки, не баллы и не рубли. Итоги ложных сигналов
показаны отдельно для каждого инструмента и горизонта, без сложения MIX с RTS.
Суммы не являются доходностью портфеля: новости/горизонты могут пересекаться.
Сохраняются указания на флаги качества исходной разметки о склейке контрактов
и синтетических долях. Заголовки и ценовые метрики подмешиваются только из
разметки с верным SHA-256. В общей таблице есть новые колонки пунктов и
направления, а в фильтрах — ложные отрицательные/положительные сигналы
и сигналы с верным/ошибочным направлением.

### Финальное обучение на годе и тест за сентябрь 2026

После фиксации настроек запустить отдельный профиль:

```powershell
# Посмотреть периоды и пути без выполнения
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --final-test --dry-run
# Разметка, обучение на годе, финальный тест, экспорт, импорт и HTML
.\.venv\Scripts\python.exe experiments_-10_10/orchestrator_RTX4070.py --final-test
```

Этот ключ задаёт обучение `[2025-09-01, 2026-09-01)` и финальный тест
`[2026-09-01, 2026-10-01)`. Разметка строится для обоих периодов до 1 октября,
поэтому котировки за сентябрь должны быть доступны в папках MIX и RTS.
Сентябрьские строки не входят в обучение и балансировку. Проверки между
эпохами отключены; loss и предсказания теста считаются после завершения обучения.
Финальный адаптер не выбирается по тестовому loss или precision/recall.
После просмотра сентября подбор настроек по его результатам превращает этот
период в валидацию; для следующего независимого теста понадобится новый период.

Отдельные результаты, без замены августовского эксперимента:

- разметка: `data/experiments_-10_10/scores_test_202609.jsonl`;
- обучение и отчёты: `data/experiments_-10_10/RTX4070_extremes_test_202609`;
- имя Ollama: `news-extremes-4070-test-202609`;
- HTML: `RTX4070_extremes_test_202609/check_model_report.html`.

Явные `--data`, `--run` и `--name` имеют приоритет над этими значениями.
Удалять старую разметку не нужно. `--delete-labels` вместе с `--final-test`
относится только к выбранной новой разметке. При продолжении цепочки также
указывать режим, например `--final-test --from-stage 5`. Если финальная
разметка уже создана, `--final-test --from-stage 4` пропустит её пересчёт.
Сохраняются удаление пересекающих границу окон и защита от перепечаток;
не все новости исходного года обязательно пройдут эти проверки.

В скриптах обучения соответствуют параметры `--train-start 2025-09-01`,
`--validation-start 2026-09-01`, `--cutoff 2026-10-01`, `--evaluation-role test`.
Имя `validation-start` технически обозначает начало отложенной выборки также
в роли test. Совместимые файлы `validation_predictions.json` и поле validation
в `data_report.json` в этом режиме содержат сентябрьский тест; роль указана
отдельным `evaluation_role`. В `training_metrics.json` тестовый loss хранится
в поле `test`. HTML явно подписан «Финальный тест».
